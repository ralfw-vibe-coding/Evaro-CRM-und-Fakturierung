Evaro API

CRM und Fakturierung — Kontakte, Geschäftspartner, Rechnungen. Es ist dieselbe Schnittstelle, über die die Weboberfläche selbst arbeitet.

OpenAPI 3.1 (YAML) llms.txt — Kurzfassung für Agenten Zur Anwendung

Die HTTP-Schnittstelle von Evaro. Es ist dieselbe Schnittstelle, über die die Weboberfläche selbst arbeitet — es gibt keinen zweiten, davon abweichenden Weg in die Daten.

Zwei Dinge, die anders sind als erwartet

1. Kein /api/kontakte/{id}. Es gibt pro Ressource genau einen Pfad. Welcher Datensatz gemeint ist, steht als id im Body, auch bei PATCH und DELETE.

2. DELETE braucht einen Body. Das ist nach RFC 9110 erlaubt, aber manche HTTP-Clients senden bei DELETE grundsätzlich keinen Body und laufen dann in einen 400er. Im Zweifel den Body explizit erzwingen (curl -X DELETE -d '{"id":"..."}', fetch(url, {method:'DELETE', body: ...})).

Authentifizierung

Jeder Pfad außer /api/auth/request-otp und /api/auth/verify-otp verlangt eine der beiden Identitäten:

  • Authorization: Bearer <JWT> — aus dem Login per Einmalcode. Läuft nach 7 Tagen ab, lässt sich aber über /api/auth/refresh verlängern.
  • x-api-key: <Schlüssel> — für Skripte und Agenten. Wird im Profil erzeugt (POST /api/profile), läuft nicht ab und ist der empfohlene Weg für alles Nicht-Interaktive.

Beide führen auf denselben Benutzer und dieselben Rechte; eine Rollentrennung gibt es nicht. Ein API-Schlüssel kann alles, was der Benutzer in der Oberfläche auch kann — auch löschen.

Fehler

Jede Fehlerantwort ist JSON mit mindestens error (deutscher Klartext). Bei 422 kommt zusätzlich fields dazu: ein Objekt, das pro beanstandetem Feld die Meldung nennt, bei Rechnungspositionen mit Pfad ("lines.0.quantity").

Tauscht ein noch gültiges Token gegen eines mit voller Restlaufzeit, so dass eine regelmäßig genutzte Sitzung nicht nach 7 Tagen hart endet.

PATCH /api/invoices

Entwurf ändern, abrechnen oder Status setzen

operationId updateInvoice Anmeldung: apiKey oder bearerAuth

Ein Pfad, drei Vorgänge. Welcher gemeint ist, entscheidet das Feld action (bzw. status):

1. {"id", "data", "vat_rate"} — ohne action: Entwurf überschreiben. Wie im CRM ein vollständiges Ersetzen, kein Teil-Update. Nur bei Entwürfen möglich. Antwortet mit {invoice, conflict}.

2. {"id", "action": "bill"} — abrechnen. Vergibt die nächste Rechnungsnummer, setzt das Rechnungsdatum auf heute, friert gp_snapshot ein und schaltet den Status auf billed. Nicht umkehrbar im Sinne der Nummer: ein späterer Rücksprung auf draft behält die vergebene Nummer.

3. {"id", "action": "status", "status": …} — Status setzen (draft | billed | paid). action darf weggelassen werden, wenn status gesetzt ist. Vergibt keine Rechnungsnummer — für den regulären Weg vom Entwurf zur Rechnung ist action: "bill" zuständig.
